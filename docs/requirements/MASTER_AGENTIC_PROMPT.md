## 1. Workspace Directory Taxonomy (Where Everything Belongs)

Whenever you read, create, or modify files in this workspace, you must adhere strictly to these directory boundaries:

### Layer 1: The Router & State (Project Root)
- `AGENTS.md`: The global command-and-control entry point. It contains high-level identity, pointers to `.ai-rules/`, and routing instructions. NEVER write application code, Terraform blocks, or database schemas here.
- `agent-config.json`: The machine-readable state and configuration variables (e.g., project IDs, dataset/database names, regions, bucket names, service credentials). This is external memory. NEVER hardcode environment variables in code or prompts; always read them from this file.
- Symlinks (`.cursorrules`, `.clinerules`, `CLAUDE.md`, `GEMINI.md`): Pointers that resolve directly to `AGENTS.md`.

### Layer 2: Modular Governance & Guardrails (`.ai-rules/`)
- Purpose: Non-negotiable technical laws and security constraints.
- Files:
  * `.ai-rules/terraform_standards.md`: IaC rules (e.g., never run destroy, use service account impersonation, enforce regional placement).
  * `.ai-rules/agent_skills_standards.md`: Standards for custom agent tools (e.g., raw REST APIs, minimal pip dependencies).
  * `.ai-rules/data_standards.md` or `.ai-rules/bq_standards.md`: Data warehousing, schema, and modeling rules.
  * `.ai-rules/frontend_standards.md` or `.ai-rules/app_standards.md`: UI and application runtime standards.
- Rule: Treat this directory as law, not literature. Never write customer business logic here.

### Layer 3: Agent Skills & Tools (`.agents/skills/`)
- Purpose: Custom, executable capabilities given to the agent to interact with external platforms, cloud APIs, or manage long-running tasks.
- Structure: Each skill has its own folder containing `SKILL.md` (instructions for the agent) and `scripts/run.py` (execution logic).
- Examples: `.agents/skills/catalog-metadata-tagger/`, `.agents/skills/api-client/`, `.agents/skills/data-profiler/`.
- Rule: Only agent tools belong here. Standard customer application code (web apps, pipelines, microservices) DOES NOT belong here; it belongs in `src/`.

### Layer 4: Intent & Context (`docs/`)
- `docs/requirements/`: Raw human inputs, customer meeting transcripts, customer RFPs, legacy schemas, and architectural diagrams.
- `docs/design/`: AI-generated modular feature intents named sequentially: `docs/design/DESIGN-{XX}-{feature_name}.md`.
- `docs/llms.txt`: The machine-readable system architecture summary, data topology, and schema contracts used to maintain cross-feature compatibility.

### Layer 5: Automated Verification (`evals/`)
- Purpose: Autonomous self-correction loops and definition of done validation.
- Files: `evals/prompts.json` (test fixtures) and `evals/tests/` (executable test scripts).
- Rule: If code tests the AI or checks deployed infrastructure status, it belongs here.

### Layer 6: Knowledge Map (`graphify-out/`)
- Purpose: The queryable dependency graph of the codebase generated by Graphify.
- Files: `graph.html`, `graph.json`, and `GRAPH_REPORT.md`.
- Rule: Auto-generated dependency mappings only. Do not manually edit.

### Layer 7: The Execution Layer (`src/` & `terraform/`)
- `terraform/`: Root deployment orchestrator (`main.tf`, `variables.tf`, `outputs.tf`).
- `terraform-modules/`: Parameterized, reusable infrastructure blocks.
- `src/`: The single source of truth for all customer application source code:
  * `src/app/` or `src/service/`: Web applications, APIs, microservices, UI templates, Dockerfiles.
  * `src/pipelines/` or `src/jobs/`: Data processing jobs (Spark, Dataflow, Python ingestion scripts).
  * `src/sql/`: Production DDL, DML, stored procedures, and BigQuery ML training scripts.

## 2. Your Autonomous PoC Kickoff Workflow

When a user initiates a new PoC or lab, execute the following four phases in exact order:

### Phase 1: Ingest Context & Synthesize Architecture
1. Read all customer artifacts staged in `docs/requirements/` and environment variables in `agent-config.json`.
2. Generate or update `docs/llms.txt` with a clean, machine-readable summary of the end-to-end architecture, including:
   - Data plane topology (ingestion, processing, and storage systems).
   - Core database, lakehouse, or warehouse schemas.
   - Machine learning models, AI agents, or analytics engines.
   - Application services, APIs, and client-facing interfaces.

### Phase 2: Decompose Solution into Modular Feature Slices
Dynamically decompose the customer solution into sequential, standalone design documents saved under `docs/design/DESIGN-{XX}-{name}.md`. 

Follow this universal cloud engineering progression, tailoring names to the customer's specific workload:
- `docs/design/DESIGN-01-foundations-and-infra.md`: Core infrastructure, networking, IAM, foundational storage, and message queues.
- `docs/design/DESIGN-02-data-layer.md`: Data ingestion, pipeline processing, historical seeding, or schema migrations.
- `docs/design/DESIGN-03-analytics-and-ml.md`: Analytics transformations, machine learning models, or agentic reasoning logic.
- `docs/design/DESIGN-04-application-layer.md`: Serving layer, APIs, Cloud Run services, or user-facing interfaces.
- `docs/design/DESIGN-05-verification.md`: Automated testing, operational runbooks, and end-to-end validation.

Each `DESIGN` file must state:
1. Business Objective.
2. Exact schemas, endpoints, and technologies to use.
3. Acceptance criteria.

### Phase 3: Define the Verification Suite (`evals/`)
Populate `evals/prompts.json` with automated test fixtures that will verify every layer upon completion (e.g., verifying infrastructure deployment status, database row counts, API response codes, and model metrics).

### Phase 4: Await Execution Approval
Present an executive summary of the proposed architecture and the `DESIGN` roadmap to the human engineer. 
HALT and await human confirmation before generating any code or provisioning cloud resources.

## 3. Rules of Execution During the PoC

Once approved to execute a design file (e.g., when the user prompts `Execute docs/design/DESIGN-01-foundations-and-infra.md`):
1. **Target the Right Directory:** Write Terraform files ONLY to `terraform/`, application/pipeline code ONLY to `src/`, agent tools ONLY to `.agents/skills/`, and test scripts ONLY to `evals/`.
2. **Obey `.ai-rules/` Automatically:** Never violate rules in `.ai-rules/`. Do not prompt the user for permission to follow rules; follow them inherently.
3. **Reference `agent-config.json` Directly:** Read project IDs, dataset names, regions, and credentials directly from `agent-config.json`. Never output placeholders like `REPLACE_ME` once state is configured.
4. **Never Micro-Prompt:** When instructed to execute a design document, complete the entire feature slice, verify it, and report the state inspection results back to the user.
